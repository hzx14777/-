# 警院智慧考试平台 · 服务器配置需求分析

> 2026-11-03 | 基于当前已部署版本的实测数据推算，供立项、采购、答辩使用

## 一、项目现状画像（实测，非估算）

| 维度 | 实测值 |
|---|---|
| 运行形态 | 单进程 Node（`yj-bff/server.js`），同源托管前端静态页 + `/yjapi` 接口，端口 80 |
| 进程占用 | 工作集约 6 MB，累计 CPU 时间 0.5 秒（空闲态近零） |
| 接口吞吐 | 600 请求 / 并发 64：**4878 rps**，p50 13 ms，p95 27 ms，max 31 ms（本机 i7-13645HX / 16 GB） |
| 数据体量 | `db.json` **318 KB**：41 题 / 5 卷 / 5 考试 / 14 份答卷 / 5 用户 |
| 前端产物 | `dist` 9.2 MB / 594 个文件；首屏 gzip 后约 0.6–1 MB，全量懒加载 chunk 合计 gzip 2.2 MB |
| 外部依赖 | 无数据库、无 Redis、无消息队列、无外网 API（AI 命题是本地引擎） |

一句话：**当前版本的资源需求极低，一台入门级云主机绰绰有余；真正决定配置的不是这个版本，而是“要上多少人、要不要存三年数据、能不能停”。**

## 二、服务器需求的决定因素

### 1. 并发量（最直接的因素）
考试场景的并发不是“平均在线”，而是三个尖峰叠加：

- **开考尖峰**：整点统一开考，同一分钟内几百人同时登录、拉试卷；
- **心跳与自动保存**：每人每 30 秒 1–2 次请求，是持续的基线压力；
- **交卷尖峰**：结束前 5 分钟集中交卷，瞬时并发可达在线人数的 1/3。

按全院规模测算（5000 在校生、分 2–3 批、单批 1000 人同时在线）：

```
基线：1000 人 × 2 请求 / 30 秒 ≈ 67 rps
交卷：1000 人集中在 30 秒内交卷 ≈ 33 rps（峰值按 3 倍算 100 rps）
合计峰值：约 100–200 rps
```

对照实测 4878 rps，**余量在 20 倍以上**。也就是说并发不是瓶颈，2 核足够；把预算花在内存和磁盘可靠性上更划算。

### 2. 数据存储（决定磁盘与数据库选型）
- 单份答卷（含事件流、逐题得分）约 8–15 KB；
- 5000 人 × 每年 8 场 × 12 KB ≈ **480 MB/年**，三年约 1.5 GB；
- 题库图片、导入的课件附件是大头，按每场 200 张图 × 300 KB ≈ 60 MB/场，三年约 1.5 GB；
- 日志、审计、备份按数据量的 3 倍预留。

结论：**系统盘 40 GB 起步，数据盘 100 GB 可支撑三年**。存储不是容量问题，而是**可靠性问题**——当前是单文件 JSON，全量读写、无事务、无法多实例，这才是必须在上生产前改掉的地方。

### 3. 计算负载（决定了要不要 GPU / 高主频）
- 客观题判分、双达标计算、统计聚合：纯字符串比较与加减，单次 < 1 ms，可忽略；
- 简答要点匹配：关键词匹配 + 置信度，仍是 CPU 轻负载；
- **AI 命题**：当前是本地模板引擎；若换成真实大模型，算力在**服务商侧**（走 HTTP API），本地只增加网络等待，**不需要 GPU 服务器**；
- 唯一偏重的是前端构建（`vite build` 约 90 秒），但这是发版动作，不在服务器运行路径上。

结论：**不需要高主频、不需要 GPU**，2–4 核通用型 CPU 即可。

### 4. 部署环境（决定了系统与网络方案）
| 因素 | 现状 | 上生产要注意 |
|---|---|---|
| 操作系统 | Windows 10/11 + 计划任务自启 | 生产建议 Linux（systemd 托管、免登录运行）；若校方只给 Windows，现有脚本可直接用 |
| 端口 | 80（被占自动降 8090） | 需要 80/443 的绑定权限；校园网内可能需报备 |
| 网络位置 | 本机 / 局域网 `10.1.1.131` | 纯校内使用走内网千兆，**不必买公网带宽**；要外网访问才需公网 IP + 带宽 |
| HTTPS | 无 | 涉及学号姓名成绩，建议配证书（免费 DV 证书即可） |
| 域名 | IP 直连 | 建议一个校内域名，便于换机与发证 |

### 5. 可用性与运维（最容易被忽略，却最影响考试）
- 考试期间**不可中断**：单进程 = 单点，进程崩溃即全场中断；
- 需要有**每日自动备份**（当前把 `db.json` 拷走即可，改 MySQL 后做定时 dump）；
- 需要**磁盘快照**，防误删与勒索；
- 要有**监控与告警**（端口探活 + 磁盘余量），否则故障只能等学生反馈。

### 6. 带宽（按首屏体积算，不按人数拍脑袋）
首屏 gzip 约 0.8 MB。1000 人集中在 10 分钟内完成首屏：

```
1000 × 0.8 MB = 800 MB / 600 s ≈ 11 Mbps（平均），峰值按 2–3 倍 → 30 Mbps
```

结论：**校内千兆内网零压力；公网部署建议 50 Mbps 或分批开考**。静态资源可加 Nginx 缓存/压缩，把首屏压到 400 KB 以内。

## 三、三档配置建议

### A 档 · 答辩演示 / 单机试用（当前阶段，够用即可）
| 项 | 建议 |
|---|---|
| 形态 | 现有笔记本即可；要独立主机就用**轻量应用服务器** |
| 规格 | 2 核 / 2 GB / 40 GB SSD / 3–5 Mbps |
| 系统 | Ubuntu 22.04 或 Windows Server 2019+ |
| 说明 | 实测 6 MB 内存占用，2 GB 内存能跑到 200+ 并发；答辩演示完全够 |
| 费用量级 | 云厂商轻量 60–120 元/月；校内虚机 1 台即 0 成本 |

### B 档 · 系部试点（推荐作为正式上线起点）
| 项 | 建议 |
|---|---|
| 规模 | ≤2000 人、单场 ≤300 并发 |
| 规格 | **2 核 / 4 GB / 100 GB SSD / 5 Mbps**（或校内虚机 4 核 8 GB） |
| 部署 | Nginx（443 + 静态缓存）+ Node 单实例（systemd）+ MySQL 8 同机 |
| 说明 | 4 GB 是给 MySQL 留的余量（`innodb_buffer_pool` 1 GB）；这个档位能撑住“一个系整建制考试” |
| 费用量级 | 云 ECS 通用型 150–250 元/月；云数据库另计 200–400 元/月（可先用同机 MySQL 省掉） |

### C 档 · 全院生产（5000 人、多批次、要稳）
| 角色 | 规格 | 说明 |
|---|---|---|
| 应用服务器 | **4 核 / 8 GB / 100 GB SSD** | 跑 2 个 Node 实例（PM2/systemd）+ Nginx，滚动重启不中断 |
| 数据库 | **4 核 / 8 GB / 200 GB SSD**（或云 RDS 2 核 4 GB） | 独立部署，避免与应用抢内存；每日全备 + binlog |
| 文件存储 | 对象存储 50 GB 或 NAS | 题库图片、导入导出、备份归档 |
| 带宽 | 校内千兆 / 公网 50 Mbps | 首屏 0.8 MB，分批开考压力更低 |
| 备份 | 每日全量 + 每周异地 | 数据量小，成本可忽略但必须做 |
| 费用量级 | 自建虚机 0 元（校内资源）；公有云约 600–1200 元/月 | |

## 四、为什么是这些数字（取舍理由）

1. **CPU 给 2 核就够**：实测 4878 rps 只用了 0.5 秒 CPU 时间；Node 单线程模型下一个实例吃不满 1 核，2 核的价值是“留一核给系统与 GC 抖动”。
2. **内存优先于 CPU**：Node 常驻内存小，但 MySQL 8 默认就要 1–2 GB，把 4 GB 作为 B 档下限是为数据库留位置，而不是为 Node。
3. **磁盘看可靠性不看容量**：三年数据不到 5 GB，100 GB 全为日志、备份、快照留白；选 SSD 是因为考试写入需要稳定 IOPS，不是为了容量。
4. **不买单 GPU / 高主频**：AI 命题走外部 API，本地无推理负载；判分是字符串运算。
5. **不建议保留砚考 Java 微服务全家桶**：实测 14 个服务常驻约 7.5 GB 内存、启动 5–7 分钟，为了一个演示场景要 8 核 16 GB，性价比极低。当前 Node 单进程方案用 1/100 的资源实现了同等业务链路。
6. **公网带宽不是必选项**：考试发生在校内，走内网既快又安全；确需外网访问再单开 20–50 Mbps。

## 五、上生产前必须做的工程改造（比加配置更重要）

按优先级：

1. **换掉 JSON 文件存储**，改 MySQL 8（按 SRS 第 7 章的 9 大实体建表）——现在两个考生同时交卷会互相覆盖，这是功能性缺陷，不是性能问题；
2. **反向代理 + 多实例**：Nginx 前置，Node 跑 2 个实例，支持不停机发版与单实例故障接管；
3. **备份与恢复演练**：每日 dump + 每周验证能恢复，别只备份不演练；
4. **监控告警**：端口探活、磁盘余量、错误日志关键字，接入校内监控或轻量方案（Uptime Kuma）；
5. **HTTPS 与访问控制**：证书 + 管理端 IP 白名单；
6. **押题/开考错峰**：把统一开考拆成分批，直接从架构上削掉尖峰，比加机器便宜。

## 六、给采购/答辩的一句话结论

> 现阶段（答辩演示）一台 **2 核 2 GB** 的机器即可运行；正式用于系部考试建议 **2 核 4 GB + 100 GB SSD**；全院规模建议 **4 核 8 GB 应用 + 4 核 8 GB 数据库**，且优先使用校内虚拟化资源而非公有云。瓶颈不在算力，而在存储改造与高可用。
