## 一、为什么选项目一

选型报告给砚考的评分是 **88 分（第一）**，核心原因在改造过程中被验证：

| 维度   | 砚考现状                                                                                                                                       | 对改造的意义                                                 |
| ---- | ------------------------------------------------------------------------------------------------------------------------------------------ | ------------------------------------------------------ |
| 技术底座 | Spring Cloud Alibaba + Nacos + Gateway + Dubbo，14 个微服务；前端 Vue3 + TypeScript + Vite + Element Plus                                          | 与需求文档「React 技术基线」不同，但工程结构完整，可直接承接业务；前端已具备路由、权限、字典、请求封装 |
| 数据模型 | `question / paper / paper_question / exam / exam_certificate / exam_proctor_event / exam_mark_item / wrong_question / stat_exam_*` 共 28 张表 | 与需求文档第 7 章九大实体高度同构，缺的只是「知识点组」与「资格」两层                   |
| 已有能力 | 五题型题库、手动/随机组卷、限时作答、客观题自动判分、防作弊事件采集、错题本、统计分析、AI 命题服务                                                                                        | 主链路 80% 可直接复用，不必从零搭                                    |
| 许可   | MIT                                                                                                                                        | 可商用改造，无 AGPL 传染风险                                      |

**结论**：沿用砚考的工程底座与页面框架，按需求文档补齐「双达标判定 / 人机共判 / AI 命题闭环 / 准入资格」四条差异化链路。这也是选型报告给出的备选路线——「复用砚考后端，前端按需求重做业务层」。

## 四、核心算法（可复算、可解释）

**双达标判定**（`engine.js: gradeAttempt`）

```
组满分 Gi = 试卷总分 × 组权重 wi
组得分率 = 组内实得 / Gi
通过条件：总分 ≥ 总分 × 及格比例 P（默认 0.7）
         且 ∀i：组得分率 ≥ Ri（默认 0.6）
失败分型：total（仅总分不足）/ group（总分够、某组偏科）/ both
```

演示数据刻意复刻了需求文档 6.5 的示例：张予安总分 **78.5**（≥70 及格线），但「时空分析」组得分率仅 **40%**（30 分组只得 8 分），判定未通过，并直接给出该组的补强入口。

**评分规则**（6.4）

- 单选/判断：完全匹配
- 多选：全对满分、漏选半分、错选 0 分
- 填空：去空格、统一全半角、忽略大小写、支持同义词
- 简答：按评分要点逐点匹配，得分 = Σ(命中要点权重) × 题分；置信度由命中率与答案长度共同决定，< 0.75 强制人工复核

**取分与积分**（6.6 / 6.9）

- 取历次最高分，但资格判定以「最高分且双达标」的答卷为准
- 首次通过计分：随堂测 5 / 专项卷 20 / 准入卷 30，≥85 分额外 10 分
- 资格有效期 12 个月，重考提分则延期并更新等级

## 六、五分钟演示动线

1. **学生视角**：`/yj/login` → 张予安登录 → 考试大厅（三类分区、未解锁卡片显性展示前置章节）
2. 打开「项目准入卷」→ 详情页看判定规则（四个知识点组、权重、达标线）→ 勾选须知进入答题
3. 答题页演示：五题型控件、答题卡、自动保存、倒计时、切屏被记录
4. 直接查看历史成绩 `/yj/result/att_seed_03`（张予安 78.5 分）：**总分达标但时空分析 40% 未达标** → 逐题解析 + 补强入口
5. 错题本按知识点聚合 → 标记已掌握；准入资格页看「Python 专项技能卷」资格卡
6. **教师视角**：右上角切换为陈立群 → AI 命题工作台走完三步（选「案件数据清洗」→ 12 题 → 提交 → 看自检与溯源）→ 批量通过入库
7. 阅卷中心：挑低置信度答卷 → 看 AI 要点命中/缺失 → 确认 → 弹窗显示双达标结论与资格发放
8. 分析看板：成绩分布、知识点雷达、题目质量标注
9. 审计页：命题、发布、阅卷、跨平台事件的留痕

## 七、与需求文档的差距（如实说明）

| 项                  | 现状                                | 原因与后续                                                       |
| ------------------ | --------------------------------- | ----------------------------------------------------------- |
| SSO 统一登录           | 平台内自签会话，未接论坛 OIDC                 | 演示环境无认证中心；接口层已预留 `Authorization: Bearer` 透传                 |

| 跨平台事件              | 事件已生成并可查看，未真实投递到工坊/论坛             | 无下游系统；事件体结构与 `eventId` 幂等位已就绪                               |
| 前端技术栈              | Vue3 + Element Plus（沿用砚考）         | SRS 要求 React + AntD5；本次优先复用开源底座，未做框架替换                      |

| 砚考原后台页面            | 保留但需启动 Java 栈                     | 与本次业务模块并行存在，互不干扰                                            |

## 八、工程备注

- 砚考原后端要求 JDK17 / MySQL8 / Redis7 / Nacos2，运行时位于 `C:\yk-runtime`（见《砚考本地运行说明.md》）。
- 适配服务无第三方依赖，仅用 Node 内置模块，`node server.js` 即可起。
- 判分、双达标、取分三处算法均在 `engine.js` 中集中实现，符合 SRS 9.6「规则不散落在页面逻辑」的要求。
- 演示数据中的题目、课程、知识点均围绕「数据警务 / 网络安全」专业课程编写，可追溯到章节正文，满足 G1「教考同源」的可验证性。
